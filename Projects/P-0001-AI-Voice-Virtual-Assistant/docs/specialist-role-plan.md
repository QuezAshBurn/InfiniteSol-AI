# Specialist role plan for P-0001 AI Voice Virtual Assistant

**Owner:** Project Manager  
**Revision:** v1.1  
**Date:** 2026-11-21 AWST  
**Status:** Proposed assignments. Each specialist starts when the PM records a scoped Markdown work authorization approved by the applicable authority.

This plan applies the [shared role catalog](../../../AI%20Team/ROLE-CATALOG.md) to the existing Phase 1 build. The [project record](../project-record.md), [charter D6 v1.2](../discovery/D6-draft-charter.md#13-ceo-build-approval), [requirements D1 v1.2](../discovery/D1-requirements.md), [architecture D2 v1.2](../discovery/D2-architecture-brief.md), and [evidence plan D5 v1.1](../discovery/D5-evidence-plan.md) control the assignment proposals below. Phase 1 receives WhatsApp voice notes and replies in text in the detected language. Evidence uses the two synthetic tenants and the AUD 0 ceiling. Live voice and audio replies sit under the separate Phase 2 decision.

## Decisions to resolve before dependent assignments and release

1. **Approval references.** D6 §13 records CEO approval of v1.2. Its header and §12 still say approval is pending, and the project record's authoritative-approval field points to discovery. The PM should reconcile the current records against §13 and preserve the signed version. Confirm the approval status of the requirements, architecture and scoped tasks before relying on them.
2. **Verification baseline.** The build log reports implementation complete and lists E-001 through E-009 as pending. Its IDs diverge from D5 v1.1. For example, D5 E-003 is booking failure recovery and E-004 is tenant isolation, while the build log uses those IDs for duplicate booking and failure recovery. The BA and QA should reconcile the entire mapping before results are attached to a candidate. Include explicit coverage for retry and duplicate prevention, handoff, and D6's five-turn booking target with an agreed turn definition.
3. **Booking recovery and confirmation.** D6 §8 leaves OQ-001 open on a second confirmation. D5 E-003 allows retry or handoff, while D6 §3 specifies an automatic search for the nearest available slot after failure. The BA should bring both to the PM for a recorded disposition. In the proposed acceptance example, QA captures the failed tool result, verifies the reply avoids claiming success, verifies a nearest-slot lookup and offer or human handoff when no slot exists, and checks that accepting an alternate still passes the approved confirmation gate.
4. **Candidate and readiness.** The project record has no peer disposition or release QA evidence for the exact candidate. Reconcile D6 §6 blocking checks, including Meta approval, vendor and free-tier limits, hard cost stops and target-language detection. Keep release pending until the approved release and environment gates have current evidence.

| Field | Proposed terms |
|---|---|

Map the approved introduction, all four menu paths, booking and confirmation, recovery, handoff, language, tenant knowledge and tool permissions to the candidate and proposed independent checks. Mark each gap with a requirement, source location, expected evidence and follow-up owner. QA reviews coverage for completeness under an approved verification assignment. |
| Local scope and limits | Read the governing project Markdown, `build/` and synthetic fixtures. Write only the approved review output under `docs/`. AUD 0 and synthetic data only. This review excludes code changes, running scenarios, external services, deployment and production traffic. |

The PM can propose separate Copywriter and Content Strategist assignments after the first review. Record fixes and test execution in their own approved tasks. The two senior developers continue independent peer review, QA owns independent acceptance and regressions, and the Technical Writer updates the document register and applicable change, build and handoff records. The PM escalates changes to scope, spend and Production approval to the CEO.

## Proposed evidence for confirmation and recovery

Use this handoff when the BA and QA reconcile D5 scenarios E-002 and E-003 with the current requirements and candidate. The expected behavior below is for planning. Record test execution separately under an approved QA assignment.

| Scenario | Tech Lead and developer evidence | UX Designer and Copywriter evidence | Independent QA evidence |
|---|---|---|---|
| Customer sends an ambiguous confirmation | Link the exact confirmation rule and candidate path. The assigned developer records the relevant application state and whether a booking tool call or write occurred on the synthetic case. | Map the clarification reply to the offered service and slot. Keep the wording clear in the supported reply language. Route any second-confirmation decision to the BA and PM. | Verify that the WhatsApp text clarifies the choice, the booking tool stays gated, and no booking is written. Compare the user-visible result and backend state for the same synthetic case. |
| Booking fails after a clear confirmation | Trace the failed tool result, nearest-slot lookup and retry handling. The assigned developer records the tool outcomes and booking state against the exact candidate. | Specify the text for the nearest-slot offer or handoff when no slot is available. Keep the original failure clear and reconfirm the alternate under the approved rule. | Verify the text matches the tool outcome, the alternate is offered or the handoff is offered, and a retry creates at most one booking. Check that the assistant claims success only after a successful booking result. |

## Role design review

Claude Code completed a follow-up review of all eight roles on 2026-11-21 using the project requirements stated in the conversation. Its earlier review used a fictional scheduling assistant. The PM's local plan incorporates distinct engineering, dialogue and independent QA evidence for ambiguous confirmation and booking failure, plus tenant-scoped conversion measurement. The review did not receive local project files. The Phase 1 channel, booking recovery rule and approval findings were checked locally against the governing Markdown.

The local plan keeps the Copywriter on Phase 1 WhatsApp replies after the UX flow and BA rules are ready. The Solution Architect owns technical design and the Tech Lead owns implementation conformance. The follow-up review's suggestions about slot holds, spoken output, custom screens and public search apply only if separately approved. Private tenant RAG sources stay under the project and tenant content approval process.
