# Delivery phases, environments and GitHub tracking

The implementation phases are Development, Testing, Staging and Production. They follow discovery, optional prototyping, architecture decisions and build approval. A phase records what work happened. An environment is the isolated place where the team carries it out. The architect defines the intended boundaries and parity. The PM and developers verify which environments and workflows actually exist before assigning checks.

| Phase and environment | Work and owner | Evidence to move forward |
|---|---|---|
| **Development** | Author builds on a feature branch or worktree and follows the coding standard. Peer independently reviews code and docs before integration. | Scoped change, peer disposition, relevant checks, source commit and integrated release artifact identity. |
| **Testing** | QA verifies requirements, applicable regressions and failure paths in an isolated QA environment. Use test data with no live effects. | Candidate ID, configuration and dataset versions, actual QA and automated results, addressed blockers. |
| **Staging** | The Deployment Engineer coordinates rehearsal with the **same artifact** in a production-like environment. Record parity gaps. Verify smoke, integrations, configuration and, where applicable, migration, rollback or recovery. | Observed checks and run IDs, artifact match, rollout and rollback evidence, parity risk disposition and support readiness. |
| **Production** | The authorised operator deploys the **exact artifact approved for release** by the CEO. Confirm the live version, run authorised smoke and health checks, and hand off to support. | Approval linked to version and configuration scope, deployment and observed health evidence, rollback status, and support handoff. |

Build one identifiable integrated release artifact for Testing, Staging and Production. Record its immutable digest or release package identity and source commit. Promote that artifact without rebuilding it. A changed artifact becomes a new candidate and repeats required verification before promotion. A material configuration change requires impact review, rerunning affected checks, and updated production approval when the previously approved scope no longer matches. Keep environment-specific endpoints, data and credentials separate. Record their versions or safe references. Do not record secret values. Resolve missing required environments, failed checks, unknown artifact identity and material parity gaps before release.

## Document every deployment

Keep a versioned release and rollback runbook and a promotion record for each release under `Projects/<Project Name>/docs/02-delivery/`. Use `starter/templates/release-runbook.md` and `starter/templates/environment-promotion.md`. Before the release decision, link rehearsal, independent QA and recovery evidence to the exact candidate and obtain the required approvals. During each attempt, log operator, actions, actual results and stop or rollback decisions. Afterwards capture post-release verification, release notes, current runbooks and support acceptance. Link the records in the document register and project record. The Deployment Engineer owns technical accuracy. The Technical Writer reconciles the affected documents and the PM checks them at the gate.

## Track delivery in GitHub

Developers track their changes from branch and pull request through the observed release. The Deployment Engineer owns the environment promotion history and release execution record. Use the project's authorised GitHub repository and actual workflows. The author opens a scoped pull request with requirements, relevant design decisions, exact revision, tests and documentation. The peer returns the independent Codex or Claude Code disposition and links its evidence to the pull request where authorised. Check configured review rules and passing checks before integration. A green workflow alone does not establish peer review or QA.

Follow the applicable GitHub Actions or deployment system run for each environment. Record the pull request, merge or source commit, build/artifact identity, run or deployment ID, release tag or release entry where used, operator, times and the observed verification outcome. A tag or commit is provenance. Verify the artifact identity and actual target environment as well. If GitHub Actions does not perform deployment, link the approved deploy system's run. Use `starter/templates/environment-promotion.md` and keep it linked from the project record. Never publish, change repository permissions or deploy outside assigned authority.

For failed or partial deployment, capture the run, observed environment state and last known deployed artifact. Stop promotion until the issue is resolved. The authorised operator follows the approved rollback path where applicable. Record the actual restored release and observed checks, then return the issue to the PM. An incident or workflow permission does not substitute for the CEO's production decision.
