# Codex and Claude Code review protocol

Use this protocol for every code change and for material non-code decisions the PM assigns to independent review. Follow the charter's access and release boundaries. The PM maintains the record and appoints the author and reviewer. For application code, the two Senior Developers are author and reviewer. The Data Engineer can author scoped pipeline, analytical model or BI code within the active build slot. In that case, a non-authoring senior developer independently reviews it. Use separate Codex and Claude Code sessions for every code change. Either runtime can take either role as tasks change. Specialists can join for their own sign-off and QA remains an independent acceptance check.

## Exchange and decision rules

1. **Freeze the packet.** Provide project and task IDs, requirements and approved scope version, artifact and candidate revision, baseline and diff if applicable, reproducible evidence, open assumptions, boundaries for tools and data, and the decision sought. Code review starts from the approved requirement, actual diff, technical change record, build evidence and affected technical docs. Verify those docs against the candidate. A design or document review starts from the approved scope, cited evidence and the proposed artifact. Use the same revision in both sessions. Share only permitted content.
2. **Challenge independently.** Load the reviewer role and packet in a separate session. Ask for evidence-backed objections and an independent disposition. The reviewer checks the actual artifact and reports what it inspected, could reproduce, and could not verify. Start the first review before presenting the author's conclusions about contentious issues. Record the runtime, role, timestamp, candidate revision, and check evidence. A self-check stays labelled a self-check in the record.
3. **Resolve.** The author fixes the issue or presents evidence for a rebuttal. Use a focused check when disagreement is factual. For competing designs, compare them against the approved criteria and let the designated decision owner resolve the tradeoff. Put the original finding, author response, verification and reviewer disposition in the ledger. Re-review changes against the new revision. The reviewer who approves a candidate must have had no authorship of it.
4. **Close or escalate.** `APPROVE` requires an exact candidate version, a real independent reviewer, all required evidence available, and no open blocking findings. Use `CHANGES REQUIRED` when an actionable issue prevents approval, or `BLOCKED` when the reviewer or essential evidence is unavailable. Count one substantive round from a packet through the reviewer's evidence-backed disposition. After three unresolved substantive rounds for the same change, or sooner if the budget or schedule is at risk, the PM escalates with both positions, an evidence gap or tradeoff, a recommended next check and the required decision. Treat `BLOCKED` as an immediate recovery event outside the substantive round count. Escalation or a CEO priority decision does not count as peer approval. Keep the gate pending until review succeeds. Any change after the approved revision starts a recheck.

When a reviewer or runtime is unavailable, the PM records the blocker immediately with the frozen candidate, missing party or capability, required reviewer runtime, recovery owner and next checkpoint. Try a fresh authorised session of the same runtime or reschedule the peer. If staffing is the issue, ask the CEO to designate another senior peer. The substitute must have no authorship of the candidate and must complete the review in a separate session on the required counterpart runtime (Claude Code if Codex authored the change, or Codex if Claude Code authored it). A third runtime or unaided human review can add evidence and does not replace the required counterpart. In the meantime the author may complete unaffected tasks within existing approval. If there is no valid peer, keep the candidate blocked, give the CEO the schedule or priority options, and retain the pending review. Escalate with the evidence and missing reviewer, even when there is only one recorded position.

## Review request you can reuse

> Act as the independent reviewer assigned to the attached project packet. Read the approved goal and versioned artifact. Identify decisions that could be made incorrectly, requirements with weak proof, internal conflicts, missing handoffs, unsafe defaults and material failure cases. Use only the provided evidence and explicitly authorised tools. For every finding provide severity, exact source or observable behaviour, impact, and a decisive verification step. Separate findings from questions. State what you actually inspected or executed. Return `APPROVE`, `CHANGES REQUIRED`, or `BLOCKED` for the specified revision. Ask for missing material when a conclusion depends on it.

## Severity and reconciliation

| Severity | Effect |
|---|---|
| Critical | Actual or reasonably suspected exposure, serious integrity loss or material service interruption. Stop affected work where authorised and escalate immediately. Label uncertainty. |
| High | A core requirement fails, a required control is absent, a significant regression is demonstrated, or a material risk lacks a necessary check. Resolve and re-verify before release. |
| Medium | A meaningful problem with bounded impact. Resolve before the relevant gate, or document explicit acceptance with an authorised owner, impact and follow-up. |
| Low | A limited or optional improvement. Record it when it helps a future decision. |

If two reviewers disagree on severity, carry the higher classification while the PM routes the dispute to the accountable specialist or decision owner. For irreversible or external actions, the applicable human authority and tool guardrails still apply.
