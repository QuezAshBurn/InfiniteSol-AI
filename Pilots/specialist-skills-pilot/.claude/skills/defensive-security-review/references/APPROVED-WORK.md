# Approved Markdown controls every assignment

**No approved Markdown, no work.** This applies to every role and every project, including discovery, prototypes, analysis, coding, testing, deployment, marketing and maintenance. Work may start only when the PM can point to a current approved project Markdown record that explicitly covers the assigned action, and when any required tool or execution permission is in place.

## Bootstrap a request

The PM may log the CEO's incoming request and prepare the proposed authorization for approval. This is an administrative intake step. Leave the status `Awaiting discovery approval`. Assign no project work, conduct no triage or discovery, and run no project checks before approval. Use `starter/templates/work-authorization.md` for the first approval. Record the CEO's dated approval against the exact file revision and allowed paths, activities, time, spend and limits. A discovery authorization can explicitly cover gathering evidence, developing draft documents and preparing a proposed baseline for approval.

## Apply the rule at every stage

| Stage | Approved Markdown required before work | What the work produces |
|---|---|---|
| Before build | Discovery authorization with scope and limits. For experiments, an approved plan explicitly covering the prototype, data, workspace and timebox. | Proposal, charter, requirements and flows, architecture, estimates, risks and prototype findings for the next decision. |
| Build and verification | CEO-approved charter and current approved requirements, business rules, relevant design and coding standard, and a scoped approved task. QA uses an approved verification assignment, acceptance criteria and plan. | Implementation, technical change records, build evidence, peer dispositions, QA results and updated specifications and procedures. |
| Release and handoff | Approved rehearsal plan for Staging, plus current release and rollback runbook and CEO approval for the exact Production candidate and configuration scope. Marketing and support each use an approved assignment and applicable permissions. | Deployment attempt and verification records, release notes, support acceptance, closeout and current operating documents. |
| After release | Approved maintenance assignment or incident runbook covering the particular action and limits. New changes and releases follow the applicable approval gates. | Incident and maintenance records, verified updates, current docs and improvement proposals. |

Keep the approved records in `Projects/<Project Name>/`. The project document register identifies the controlling path, exact revision or immutable snapshot, approval status and dated decision reference. Scope, spending and Production decisions stay with the CEO. PM and specialists approve only within expressly delegated authority and record that authority. Keep each signed version or an immutable copy. Apply the same rule to work done locally and through tools.

Every role reads the controlling files before work and cites them in its outputs and handoffs. An approved task or story must state an observable goal, measurable acceptance criteria, applicable required steps or constraints and independent verification ownership. Apply `workflows/GOAL-AND-QUALITY.md` before claiming completion. Drafts and test evidence can be produced within an approved assignment. They become controlling instructions only after the applicable approval. Record factual outcomes when observed, including failures, and link their evidence. Approval of an instruction does not turn an unverified outcome into a verified one.

If an approval is absent, stale, superseded, conflicting, incomplete or outside scope, stop affected work and give the PM the exact missing item, risk and unblock condition. Do not fill gaps with chat history, code assumptions or another project's practices. When implementation differs from approved requirements or design, document the discrepancy and obtain a resolution before dependent work proceeds. Resume on the exact approved revision and rerun affected checks. Record any already-authorised containment action under the applicable incident runbook. A critical-incident build pause requires a current, scoped and dated CEO-approved Markdown delegation with a qualifying threshold, time limit and named delegate. Only the pause is delegated through that decision. Commercial actions and rehearsals follow the approved scope and execution permissions in `workflows/BUSINESS-OPERATIONS.md`. Keep every material decision, logic rule, change, build, verification result and handoff linked in the project documentation.
